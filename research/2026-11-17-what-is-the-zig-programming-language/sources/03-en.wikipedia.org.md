**Zig** is a general-purpose [system programming language](https://en.wikipedia.org/wiki/System%5Fprogramming%5Flanguage "System programming language") that emphasizes [performance](https://en.wikipedia.org/wiki/Computer%5Fperformance "Computer performance"), simplicity and [metaprogramming](https://en.wikipedia.org/wiki/Metaprogramming "Metaprogramming").[\[9\]](#cite%5Fnote-:1-9) The [compiler](https://en.wikipedia.org/wiki/Compiler "Compiler") is [free and open-source software](https://en.wikipedia.org/wiki/Free%5Fand%5Fopen-source%5Fsoftware "Free and open-source software"), released under an [MIT License](https://en.wikipedia.org/wiki/MIT%5FLicense "MIT License") on [Codeberg](https://en.wikipedia.org/wiki/Codeberg "Codeberg").[\[10\]](#cite%5Fnote-10)

Zig was designed to replace the [C programming language](https://en.wikipedia.org/wiki/C%5F%28programming%5Flanguage%29 "C (programming language)") while maintaining C [ABI](https://en.wikipedia.org/wiki/Application%5Fbinary%5Finterface "Application binary interface") compatibility.[\[11\]](#cite%5Fnote-11)[\[12\]](#cite%5Fnote-12) Unlike C, which supports metaprogramming through [preprocessor macros](https://en.wikipedia.org/wiki/Preprocessor%5Fmacro "Preprocessor macro"), Zig supports metaprogramming through compile-time code execution.[\[13\]](#cite%5Fnote-:2-13) At [compile time](https://en.wikipedia.org/wiki/Compile%5Ftime "Compile time") types are [first class](https://en.wikipedia.org/wiki/First-class%5Fcitizen "First-class citizen") and can be passed to functions, this system is used for [generics](https://en.wikipedia.org/wiki/Generic%5Fprogramming "Generic programming").[\[13\]](#cite%5Fnote-:2-13)[\[14\]](#cite%5Fnote-14) A core goal of the language is to have no hidden [memory allocations](https://en.wikipedia.org/wiki/Memory%5Fmanagement "Memory management") or [control flow](https://en.wikipedia.org/wiki/Control%5Fflow "Control flow")[\[9\]](#cite%5Fnote-:1-9). [Low-level programming](https://en.wikipedia.org/wiki/Low-level%5Fprogramming%5Flanguage "Low-level programming language") features include packed [structs](https://en.wikipedia.org/wiki/Record%5F%28computer%5Fscience%29 "Record (computer science)"), arbitrary-width [integers](https://en.wikipedia.org/wiki/Integer%5F%28computer%5Fscience%29 "Integer (computer science)")[\[15\]](#cite%5Fnote-15) and multiple [pointer](https://en.wikipedia.org/wiki/Pointer%5F%28computer%5Fprogramming%29 "Pointer (computer programming)") types.[\[13\]](#cite%5Fnote-:2-13)

Zig was designed by Andrew Kelley and first announced in 2016.[\[1\]](#cite%5Fnote-ziginit-1) Development is funded by the Zig Software Foundation (ZSF), which receives corporate sponsorships as well as private donations.[\[16\]](#cite%5Fnote-16)[\[17\]](#cite%5Fnote-17)

## History

\[[edit](/w/index.php?title=Zig%5F%28programming%5Flanguage%29&action=edit&section=1 "Edit section: History")\]

Andrew Kelley began making a [digital audio workstation](https://en.wikipedia.org/wiki/Digital%5Faudio%5Fworkstation "Digital audio workstation") but was unsatisfied with [Go](https://en.wikipedia.org/wiki/Go%5F%28programming%5Flanguage%29 "Go (programming language)"), [Rust](https://en.wikipedia.org/wiki/Rust%5F%28programming%5Flanguage%29 "Rust (programming language)") and [C++](https://en.wikipedia.org/wiki/C++ "C++"). He decided to make a new language with the advantages of C while improving on its weaknesses.[\[18\]](#cite%5Fnote-18) The name _Zig_ was chosen using a script that generated random combinations of letters starting with the letter _z_.[\[19\]](#cite%5Fnote-19)

The previous [bootstrapping](https://en.wikipedia.org/wiki/Bootstrapping%5F%28compilers%29 "Bootstrapping (compilers)") compiler was written in Zig and C++ and it used [LLVM](https://en.wikipedia.org/wiki/LLVM "LLVM") as a back-end.[\[20\]](#cite%5Fnote-20) It was replaced with a fully Zig version in the 0.11.0 release. Zig now uses a prebuilt [WebAssembly](https://en.wikipedia.org/wiki/WebAssembly "WebAssembly") binary to bootstrap itself.[\[21\]](#cite%5Fnote-21)[\[22\]](#cite%5Fnote-22)

On 26 November 2025, Zig development migrated from [GitHub](https://en.wikipedia.org/wiki/GitHub "GitHub") to [Codeberg](https://en.wikipedia.org/wiki/Codeberg "Codeberg"), citing GitHub's declining reliability under Microsoft ownership, particularly due to poor use of [Generative AI](https://en.wikipedia.org/wiki/Generative%5FAI "Generative AI") on the platform, as a primary reason for this change.[\[23\]](#cite%5Fnote-officialMigrationAnnouncement-23)[\[24\]](#cite%5Fnote-theRegisterMigration-24) One cited example of the platform's declining reliability was the apparent unreliability and delays towards the fixing of bugs in GitHub's [CI](https://en.wikipedia.org/wiki/Continuous%5Fintegration "Continuous integration") platform, GitHub Actions.[\[23\]](#cite%5Fnote-officialMigrationAnnouncement-23)[\[24\]](#cite%5Fnote-theRegisterMigration-24) In addition, the Zig development team had concerns with the Generative AI direction of GitHub, which was in contrast to the Zig project's policy against Generative AI.[\[25\]](#cite%5Fnote-25) In 2026, Codeberg would introduce a policy against Generative AI[\[26\]](#cite%5Fnote-26)[\[27\]](#cite%5Fnote-27), similar to the policy of the Zig project.

## Syntax and features

\[[edit](/w/index.php?title=Zig%5F%28programming%5Flanguage%29&action=edit&section=2 "Edit section: Syntax and features")\]

### Hello World program

\[[edit](/w/index.php?title=Zig%5F%28programming%5Flanguage%29&action=edit&section=3 "Edit section: Hello World program")\]

Below is a ["Hello, World!" program](https://en.wikipedia.org/wiki/"Hello,%5FWorld!"%5Fprogram ""Hello, World!" program") in Zig.

const std = @import("std");

pub fn main() void {
    std.debug.print("Hello, World!\n", .{});
}

### Goals

\[[edit](/w/index.php?title=Zig%5F%28programming%5Flanguage%29&action=edit&section=4 "Edit section: Goals")\]

The primary goal of Zig is to be a better solution to the sorts of tasks that are currently solved with C. A primary concern in that respect is readability; Zig attempts to use existing concepts and syntax wherever possible, avoiding the addition of different syntax for similar concepts. Further, its goal is to be a language designed for "robustness, optimality and maintainability". The small and simple syntax is an important part of that maintainability, as one of the language's goals is to allow maintainers to debug code written in Zig without having to learn the intricacies of a language they might not be familiar with.[\[28\]](#cite%5Fnote-FOOTNOTEElizabeth2017-28) Even with these changes, Zig can compile into and against existing C code; C headers can be included in a Zig project and their functions called, and Zig code can be linked into C projects by including the compiler-built headers.[\[29\]](#cite%5Fnote-FOOTNOTEYegulalp2016-29)

Error handling is handled through error types and can be handled with `catch` or `try`. Generics are achieved through compile time code generation and accommodating a form of [duck typing](https://en.wikipedia.org/wiki/Duck%5Ftyping "Duck typing") with the `comptime` directive.[\[30\]](#cite%5Fnote-30)

### Control flow

\[[edit](/w/index.php?title=Zig%5F%28programming%5Flanguage%29&action=edit&section=5 "Edit section: Control flow")\]

Unlike C, Zig uses labeled `break` and `continue` instead of [goto statements](https://en.wikipedia.org/wiki/Goto "Goto"). These act similarly to `goto`, but can only jump to the top of [code blocks](https://en.wikipedia.org/wiki/Block%5F%28programming%29 "Block (programming)") and prevent jumping past [variable](https://en.wikipedia.org/wiki/Variable%5F%28high-level%5Fprogramming%5Flanguage%29 "Variable (high-level programming language)") initialization.\[_[citation needed](https://en.wikipedia.org/wiki/Wikipedia:Citation%5Fneeded "Wikipedia:Citation needed")_\]

### Memory handling

\[[edit](/w/index.php?title=Zig%5F%28programming%5Flanguage%29&action=edit&section=6 "Edit section: Memory handling")\]

Memory allocation in the Zig standard library follows the convention that allocation is handled through `struct`s describing the action, as opposed to calling the memory management functions in [libc](https://en.wikipedia.org/wiki/Libc "Libc"). For instance, in C if one wants to write a function that makes a string containing multiple copies of another string, the function might look like this:

const char* repeat(const char* original, size_t times);

In the code, the function would examine the size of `original` and then malloc `times` that length to set aside memory for the string it will build. That malloc is invisible to the functions calling it; if they fail to later release the memory, a leak will occur. In Zig, this might be handled using a function like:

const Allocator = std.mem.Allocator;

fn repeat(allocator: Allocator, original: []const u8, times: usize) Allocator.Error![]const u8;

In this code, the `allocator` variable is passed a struct that describes what code should perform the allocation, and the `repeat` function returns either the resulting string or, using the error union type as indicated by the `!`, an Allocator.Error. By directly expressing the allocator as an input, memory allocation is never "hidden" within another function, it is always exposed to the API by the function that is ultimately calling for the memory to be allocated. No allocations are performed inside Zig’s [standard library](https://en.wikipedia.org/wiki/Standard%5Flibrary "Standard library"). Further, as the struct can point to anything, one can use alternative allocators, even ones written in the program. This can allow, for instance, small-object allocators that do not use the [operating system](https://en.wikipedia.org/wiki/Operating%5Fsystem "Operating system") functions that normally allocate an entire [memory page](https://en.wikipedia.org/wiki/Memory%5Fpage "Memory page").[\[31\]](#cite%5Fnote-zigo-31)

The optional type is also an example of a language feature that offers general functionality while still being simple and generic. They do not have to be used to solve null pointer problems; they are also useful for any type of value where "no value" is an appropriate answer. Consider a function `countTheNumberOfUsers` that returns an integer, and an integer variable, `theCountedUsers` that holds the result. In many languages, a [magic number](https://en.wikipedia.org/wiki/Magic%5Fnumber%5F%28programming%29 "Magic number (programming)") would be placed in `theCountedUsers` to indicate that `countTheNumberOfUsers` has not yet been called, while many implementations would just set it to zero. In Zig, this could be implemented as an `var theCountedUsers: ?i32 = null` which sets the variable to a clear "not been called" value.[\[31\]](#cite%5Fnote-zigo-31)

Another more general feature of Zig that also helps manage memory problems is the concept of `defer`, which marks some code to be performed at the end of a scope no matter what happens, including possible runtime errors. If a particular function allocates some memory and then disposes of it when the operation is complete, one can add a line to defer a `free` to ensure it is released no matter what happens.[\[31\]](#cite%5Fnote-zigo-31)

The Zig standard library avoids hidden allocations. Allocation is not managed in the language directly. Instead, heap access is done via the [standard library](https://en.wikipedia.org/wiki/Standard%5Flibrary "Standard library"), explicitly.[\[32\]](#cite%5Fnote-InfoWorld-32)

### Direct interaction with C

\[[edit](/w/index.php?title=Zig%5F%28programming%5Flanguage%29&action=edit&section=7 "Edit section: Direct interaction with C")\]

Zig promotes a gradual approach to portability by providing direct interoperability of Zig code with C code, allowing code from one language to call code from the other. Since 0.16.0, this is implemented through Zig's build system, by enabling C libraries to be defined within the `build.zig` file of the Zig project, to enable for the Zig code to import the C libraries through the use of the `@import` [keyword](https://en.wikipedia.org/wiki/Reserved%5Fword "Reserved word").[\[33\]](#cite%5Fnote-:0-33)

For inclusion of C code in a primarily Zig project, this is typically implemented in the `build.zig` file, in a similar fashion to the following example (note that this example is only of the relevant code):

const translate_c = b.addTranslateC(.{
    .root_source_file = b.path("src/cheaders.h"),
    .target = target,
    .optimize = optimize,
});

const exe = b.addExecutable(.{
    .name = "example",
    .root_module = b.createModule(.{
        .root_source_file = b.path("src/main.zig"),
        .optimize = optimize,
        .target = target,
        .imports = &.{
            .{
                .name = "c",
                .module = translate_c.createModule(),
            },
        },
    }),
});

The C headers can then be called in Zig code with the following code:

const c = @import("c");

c.exampleFunction();

This is in line with how Zig imports its own libraries, similarly with the `@import` directive, typically in this fashion:

const std = @import("std");

For the alternate method of utilising and calling Zig code inside a primarily C program, this is more difficult than the aforementioned, as the Zig build system focusses on a Zig-based environment. However, it is a similar setup, as the Zig build system is still utilised for such a purpose in most scenarios. As C code naturally uses C header files (`.h`) and macros, all Zig declarations, such as functions, would need to be expressed either within header files or `extern` declarations, as would be done for C interoperability with programming languages other than Zig. The following code is an example for a C project which uses Zig code, where the shared declarations between C and Zig code are contained within an `extern.h` file:

    const sharedheader = b.addTranslateC(.{
        .root_source_file = b.path("./src/extern.h"),
        .target = target,
        .optimize = optimize,
        .link_libc = true,
    });

    const zig_code = b.addLibrary(.{
        .name = "zigcodelib",
        .linkage = .static,
        .root_module = b.createModule(.{
            .root_source_file = b.path("src/zigcode.zig"),
            .target = target,
            .optimize = optimize,
            .link_libc = true,
            .imports = &.{
                .{ .name = "flags.h", .module = sharedheader.createModule() },
            },
        }),
    });


    const main_c_module = b.addModule("main", .{
        .target = target,
        .optimize = mode,
        .link_libc = true,
    });

    main_c_module.addCSourceFile(.{
        .file = b.path("src/main.c"),
        .flags = &.{ "-Wall", "-pedantic" },
    });

    const exe = b.addExecutable(.{
        .name = "example",
        .root_module = main_c_module,
    });

    exe.root_module.linkLibrary(zig_code);

    b.installArtifact(zig_code);
    b.installArtifact(exe);

Zig 0.16.0 deprecated `@cImport`, going forward C Translation will be handled via the Build System instead of using the `@cImport` language builtin, which has been 'deleted' from the language. Additionally the release deprecated `std.Build.Step.TranslateC` in favour using an explicit package dependency of the official translate-c package, which is the same implementation as the previous build step version with additional configuration options.[\[33\]](#cite%5Fnote-:0-33)

Prior to 0.16.0, the system used for C interoperability did not use the Zig build system, and instead used a `@cImport` directive only used for calling C code. This directive would often wrap an additional `@cInclude` directive, which mirrored the `#include` macro that would be seen within C code. In these prior versions of Zig, C libraries are imported in the following manner:

const c = @cImport(@cInclude("soundio/soundio.h"));

This Zig code would be functionally equivalent to the following C code with the main difference being that the library is accessed through calls to the constant identifier `c`, as seen in the current 0.16.0 example.

#include <soundio/soundio.h>

The Zig code would then be able to call functions from soundio library in the same manner as calling functions from other Zig code, As Zig uses new data types that are explicitly defined, unlike C’s more generic `int` and `float`, a small number of directives are used to move data between the C and Zig types, including `@intCast` and `@ptrCast`.[\[31\]](#cite%5Fnote-zigo-31) This is notably different from the current implementations, as Zig code would directly be able to import code from system header files, whereas the current implementation only allows for Zig code to import C code from local libraries defined within the users code.

### Compile time evaluation

\[[edit](/w/index.php?title=Zig%5F%28programming%5Flanguage%29&action=edit&section=8 "Edit section: Compile time evaluation")\]

Zig can evaluate sections of code at [compile time](https://en.wikipedia.org/wiki/Compile%5Ftime "Compile time") instead of [runtime](https://en.wikipedia.org/wiki/Runtime%5F%28program%5Flifecycle%5Fphase%29 "Runtime (program lifecycle phase)") using the `comptime` keyword. Running code at compile time provides functionality similar to [macros](https://en.wikipedia.org/wiki/Macro%5F%28computer%5Fscience%29 "Macro (computer science)") and [conditional compilation](https://en.wikipedia.org/wiki/Conditional%5Fcompilation "Conditional compilation"), without the use of a separate [preprocessor](https://en.wikipedia.org/wiki/Preprocessor "Preprocessor") language.[\[34\]](#cite%5Fnote-roadtozig1.0-34)

Types become [first-class citizens](https://en.wikipedia.org/wiki/First-class%5Fcitizen "First-class citizen") at compile time, allowing compile-time [duck typing](https://en.wikipedia.org/wiki/Duck%5Ftyping "Duck typing"),[\[35\]](#cite%5Fnote-zig%5Fdocs%5Fcompile%5Ftime%5Fparameters-35) which Zig uses to implement generic types. The example below declares a generic [linked list](https://en.wikipedia.org/wiki/Linked%5Flist "Linked list"):

fn LinkedList(comptime T: type) type;

The function takes the type `T` and produces a concrete linked-list type based on `T`.

### Input/output as an interface

\[[edit](/w/index.php?title=Zig%5F%28programming%5Flanguage%29&action=edit&section=9 "Edit section: Input/output as an interface")\]

Starting with version 0.16.0, all standard library input/output functionality in Zig requires passing an explicit `Io` instance, rather than relying on globally available I/O functions.[\[36\]](#cite%5Fnote-io-interface-36) The change addresses the "[what color is your function](https://en.wikipedia.org/wiki/Function%5Fcoloring "Function coloring")" problem common to async programming, in which functions written to support asynchronous execution are typically incompatible with synchronous callers and vice versa. Zig's approach makes an `Io` implementation an explicit parameter rather than an implicit property of a function, allowing the same code to run under different execution strategies—including a thread-based implementation (`Io.Threaded`) and an experimental, work-in-progress stackful coroutine implementation (`Io.Evented`)—without requiring separate sets of functions for synchronous and asynchronous use.[\[36\]](#cite%5Fnote-io-interface-36)

The `Io` interface also provides task-level concurrency primitives, including `Future` (for launching and awaiting individual asynchronous tasks) and `Group` (for managing many tasks that share a lifetime), along with a unified cancellation mechanism that allows in-flight operations, such as networking or file system calls, to be interrupted.[\[36\]](#cite%5Fnote-io-interface-36)

## Compiler

\[[edit](/w/index.php?title=Zig%5F%28programming%5Flanguage%29&action=edit&section=10 "Edit section: Compiler")\]

Zig also includes a C and C++ compiler, and can be used with either or both languages[\[37\]](#cite%5Fnote-37) The compiler provides many headers including the [C standard library](https://en.wikipedia.org/wiki/C%5Fstandard%5Flibrary "C standard library") (libc) and [C++ Standard Library](https://en.wikipedia.org/wiki/C++%5FStandard%5FLibrary "C++ Standard Library") (libcxx) for many different platforms. This allows Zig’s `cc` and `c++` sub-commands to act as [cross compilers](https://en.wikipedia.org/wiki/Cross%5Fcompiler "Cross compiler") similarly to [Clang](https://en.wikipedia.org/wiki/Clang "Clang").[\[38\]](#cite%5Fnote-38)[\[39\]](#cite%5Fnote-39)

Zig treats cross-compiling as a first-class use-case of the language.[\[40\]](#cite%5Fnote-zig-40) This means any Zig compiler can compile runnable binaries for any of its target platforms. The toolchain can compile to any of these targets without installing additional software.[\[31\]](#cite%5Fnote-zigo-31)

Cross-compilation is also available for variety of the operating systems. Popular UNIX-like ones and Windows are officially supported.[\[41\]](#cite%5Fnote-41) Minimal applications can and have been made for Android (with [Android NDK](https://en.wikipedia.org/wiki/Android%5FNDK "Android NDK")) or [iOS](https://en.wikipedia.org/wiki/IOS "IOS").\[_[citation needed](https://en.wikipedia.org/wiki/Wikipedia:Citation%5Fneeded "Wikipedia:Citation needed")_\]

The [LLVM](https://en.wikipedia.org/wiki/LLVM "LLVM") backend is the default for most targets, except for [SPIR-V](https://en.wikipedia.org/wiki/Standard%5FPortable%5FIntermediate%5FRepresentation "Standard Portable Intermediate Representation"), and debug-mode [x86-64](https://en.wikipedia.org/wiki/X86-64 "X86-64").[\[42\]](#cite%5Fnote-42) Zig also supports a self-hosted backend which can be enabled by using `-fno-llvm`.[\[43\]](#cite%5Fnote-43)

## Packages

\[[edit](/w/index.php?title=Zig%5F%28programming%5Flanguage%29&action=edit&section=11 "Edit section: Packages")\]

Version 0.11.0 bundles an experimental [package manager](https://en.wikipedia.org/wiki/Package%5Fmanager "Package manager"), but no official [package repository](https://en.wikipedia.org/wiki/Software%5Frepository "Software repository") is available. Instead a package is simply a URL that points to a [compressed file](https://en.wikipedia.org/wiki/Compressed%5Ffile%5Flibrary "Compressed file library"), or a [Git](https://en.wikipedia.org/wiki/Git "Git") [repository](https://en.wikipedia.org/wiki/Repository%5F%28version%5Fcontrol%29 "Repository (version control)"). Each package ideally includes a standard `build.zig` file (that the Zig compiler uses by convention to compile the source code) and a `build.zig.zon` file containing metadata with name and version of the package.[\[44\]](#cite%5Fnote-44)
